# 06 · 事件流

Web 模式下所有实时推送走 **Server-Sent Events (SSE)**。本文描述协议格式、事件清单与订阅机制。

---

## 1. 协议格式

### 1.1 传输层

```
GET /api/events HTTP/1.1
Accept: text/event-stream
Authorization: Bearer <token>
```

响应头：

```http
Content-Type: text/event-stream; charset=utf-8
Cache-Control: no-cache, no-transform
Connection: keep-alive
X-Accel-Buffering: no
```

`X-Accel-Buffering: no` 是**给 Nginx 的指令**，禁止缓冲——不加会导致事件被攒住批量下发，实时行情看起来像"卡住了"。

### 1.2 消息格式

服务端**不写 `event:` 行**，所有消息统一走默认的 `message` 类型，用信封里的 `event` 字段区分事件名：

```
data: {"event":"market:stock:update","data":[{"symbol":"sh600000","price":9.99}]}

data: {"event":"connected","data":{"ok":true}}

: ping
```

信封结构：

```go
type Message struct {
    Name string `json:"event"`
    Data any    `json:"data"`
}
```

### 1.3 为什么不用 `event:` 行

标准 SSE 支持 `event: <name>` 声明事件类型，但那样浏览器侧需要为每个事件名注册 `addEventListener`。

JCP 的会议事件名带股票代码后缀：

```
meeting:message:sh600000
meeting:message:sz000001
meeting:progress:sh600000
```

这类**动态事件名无法预注册**。因此改用统一信封，由前端 `onmessage` 统一接收后按 `event` 字段分发——`frontend/src/api/events.ts` 的 `WebEventBus` 就是这么实现的。

### 1.4 心跳

服务端每 20 秒发一条注释行保活：

```
: ping
```

作用有二：穿透 Nginx 等中间层的空闲超时；让客户端能检测连接是否还活着。

## 2. 事件清单

### 2.1 行情事件

| 事件名 | 负载 | 触发时机 |
|--------|------|---------|
| `market:stock:update` | `Stock[]` | 自选股实时行情（交易时段 3 秒，收盘 30 秒） |
| `market:orderbook:update` | `OrderBook` | 五档盘口（交易时段 1 秒） |
| `market:indices:update` | `MarketIndex[]` | 大盘指数（上证/深证/创业板） |
| `market:kline:update` | `{code, period, data[], incremental}` | K 线推送，`incremental` 标记是否增量 |
| `market:telegraph:update` | `Telegraph` | 财经快讯（30 秒） |

### 2.2 会议事件

| 事件名 | 负载 | 说明 |
|--------|------|------|
| `meeting:message:<code>` | `ChatMessage` | 某位专家的发言。**事件名含股票代码** |
| `meeting:progress:<code>` | 进度对象 | 会议进度（正在思考 / 调用工具等） |

### 2.3 系统事件

| 事件名 | 负载 | 说明 |
|--------|------|------|
| `connected` | `{ok: true}` | 连接建立确认，客户端据此判断 SSE 就绪 |
| `strategy:changed` | 策略 ID | 激活策略变更 |
| `update:progress` | `{status, message, percent}` | 自更新进度 |

## 3. 订阅机制

### 3.1 两阶段流程

```
① 客户端                                  ② 服务端
   │                                        │
   │  POST /api/market/subscribe            │
   │  {"codes":["sh600000","sz000001"]}     │
   │───────────────────────────────────────►│ 设置两层订阅状态
   │                                        │  ① Hub 全局订阅键（用于事件过滤）
   │                                        │  ② Pusher 订阅列表（决定推哪些股票）
   │  GET /api/frontend/ready               │
   │───────────────────────────────────────►│ 启动推送循环（等待此信号）
   │                                        │
   │  ◄── data: {event, data} ──────────────│
```

**顺序很重要**：`frontend/ready` 之前推送循环处于等待状态，不会推任何数据。

### 3.2 三个订阅端点

| 端点 | 方法 | 请求体 | 作用 |
|------|------|--------|------|
| `/api/market/subscribe` | POST | `{"codes":["sh600000"]}` | 订阅股票列表 |
| `/api/market/orderbook/subscribe` | POST | `{"code":"sh600000"}` | 订阅盘口（单只） |
| `/api/market/kline/subscribe` | POST | `{"code":"sh600000","period":"1d"}` | 订阅 K 线 |

K 线周期：`1m` / `1d` / `1w` / `1mo`。

### 3.3 服务端的两层订阅状态

Web 模式没有 Wails 的事件通道，因此订阅请求走 HTTP 直连：

```
HTTP 订阅端点
   │
   ├─► Hub.SetGlobalSubscription(codes)     ← 事件过滤用
   │      internal/pkg/eventbus/eventbus.go
   │
   └─► App.SetStockSubscriptions(codes)     ← 决定推哪些股票
          → MarketDataPusher.SetStockSubscriptions()
             internal/services/market_pusher.go
```

`webapi.Subscriber` 接口定义了这条通路：

```go
type Subscriber interface {
    SetStockSubscriptions(codes []string)
    SetOrderBookSubscription(code string)
    SetKLineSubscription(code, period string)
}
```

由 `App` 实现（`web_main.go` 注入）。

## 4. 事件过滤规则

### 4.1 规则表

过滤**按事件名显式声明**，不靠负载推断：

```go
var filteredEvents = map[string]bool{
    "market:stock:update":    true,   // 按订阅过滤
    "market:orderbook:update": true,   // 按订阅过滤
    "market:kline:update":     true,   // 按订阅过滤
}
```

**不在此表中的事件一律广播**（大盘指数、快讯、会议消息、策略变更等）。

### 4.2 为什么必须显式声明

曾经的实现用「从负载里提取 code/symbol 字段」来判断是否订阅。问题在于 `MarketIndex` 也有 `Code` 字段：

```go
type MarketIndex struct {
    Code string  `json:"code"`   // sh000001
    ...
}
```

于是大盘指数事件被当成"订阅了 sh000001 的事件"，而用户订阅的是 `sh600000` —— **大盘指数被错误过滤掉了**。

这个 bug 由单元测试 `TestWebBusDeliversEventWithoutKey` 捕获。

### 4.3 订阅键提取

提取逻辑用反射实现（`eventbus.eventKeys`），支持：

| 负载类型 | 提取方式 |
|---------|---------|
| 结构体 / 指针 | `Code` 或 `Symbol` 字段 |
| map | `code` 或 `symbol` 键 |
| 切片 / 数组 | **逐元素**提取（股票列表可能含多个代码） |
| 字符串 | 直接作为键 |

候选字段名按优先级：`Code` → `Symbol` → `code` → `symbol`。

提取不到键时**不过滤**（放行），避免事件丢失。

## 5. 客户端实现

### 5.1 统一订阅接口

```typescript
// frontend/src/api/events.ts
export function onEvent<T = unknown>(
  name: string,
  handler: (data: T) => void
): () => void
```

桌面模式走 `runtime.EventsOn`，Web 模式走 `EventSource`。业务代码无需区分。

### 5.2 EventSource 连接

```typescript
const token = getToken();
const url = token ? `/api/events?token=${encodeURIComponent(token)}` : '/api/events';
const source = new EventSource(url);

source.onmessage = (evt: MessageEvent) => {
  const envelope = JSON.parse(evt.data);
  const handlers = this.handlers.get(envelope.event);
  handlers?.forEach(h => h(envelope.data));
};
```

**令牌必须走查询参数**——`EventSource` API 不支持自定义请求头。

### 5.3 断线重连

浏览器原生 `EventSource` 会自动重连。服务端不主动干预。

重连后**需要重新订阅**吗？不需要——订阅状态在服务端是全局的（`Hub.globalKeys`），与连接无关。但前端会重新发一次订阅请求（`useMarketEvents` 的依赖数组为空，只在挂载时执行一次）。

### 5.4 多标签页

每个浏览器标签页建立独立 SSE 连接，但共享服务端的全局订阅状态。

这意味着：**一个标签页改了订阅，另一个标签页的推送内容也会变**。对单用户场景无影响。

## 6. Nginx 配置要求

SSE 对反向代理配置敏感。以下设置**不能删**：

```nginx
location /api/events {
    proxy_pass http://jcp_backend;
    proxy_http_version 1.1;

    proxy_buffering off;          # 必须：否则事件被攒住批量下发
    proxy_cache off;
    chunked_transfer_encoding off;

    proxy_read_timeout 3600s;     # 必须：默认 60s 会断开长连接
    proxy_send_timeout 3600s;

    proxy_set_header Connection "";  # 必须：保持长连接

    proxy_set_header Host $host;
    proxy_set_header X-Real-IP $remote_addr;
    proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
    proxy_set_header X-Forwarded-Proto $scheme;
}
```

### 常见故障对照

| 现象 | 原因 |
|------|------|
| 事件几十秒后才到 | `proxy_buffering` 没关 |
| 连接约 60 秒断开 | `proxy_read_timeout` 太短 |
| 握手后收不到任何数据 | 没调用 `frontend/ready`，或没订阅 |
| 只有大盘指数没有个股 | 订阅过滤不匹配（检查订阅的代码格式） |
| 收盘时段看不到个股 | 收盘时股票推送 30 秒一次，属正常 |

## 7. 推送频率表

由 `MarketDataPusher.getMarketPhase()` 决定：

| 时段 | 盘口 | 股票/指数 | K线 | 快讯 |
|------|------|-----------|------|------|
| 交易中 | 1 秒 | 3 秒 | 5分钟线 3 秒 | 30 秒 |
| 集合竞价 | 9 秒 | 9 秒 | — | 30 秒 |
| 午休 | — | 15 秒 | — | 30 秒 |
| 收盘 | — | 30 秒 | 日线 5 分钟 | 30 秒 |

常量定义在 `internal/services/market_pusher.go`：

```go
tickerFast     = 1 * time.Second
tickerNormal   = 3 * time.Second
tickerSlow     = 30 * time.Second
tickerKLineDay = 5 * time.Minute
```

**测试提示**：收盘时段验证个股推送需要观察 ≥40 秒，否则会误判为"没有推送"。
