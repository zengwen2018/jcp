# 09 · 安全模型

本文说明 JCP Web 模式的安全机制、攻击面与加固建议。

---

## 1. 威胁模型

JCP 是一个**单用户自托管**的股票分析工具。典型场景：个人在云服务器上部署一个实例，自己或少数信任的人访问。

**核心风险**：

| 风险 | 后果 | 缓解 |
|------|------|------|
| 实例被扫描发现 | 未授权访问 | 令牌鉴权 + 云防火墙最小放行 |
| 令牌泄露 | 攻击者可用你的大模型额度 | HTTPS + 定期轮换 |
| API Key 泄露 | 密钥被盗用、账单损失 | 脱敏机制（见 §3） |
| 提示词注入 | 通过股票名称/新闻内容诱导 LLM | 工具白名单 + 工具是只读的 |
| 资源耗尽 | 内存/带宽被打满 | 令牌 + 防火墙 + 配额限制 |

## 2. 鉴权

### 2.1 令牌机制

```go
// internal/webapi/auth.go
type AuthConfig struct {
    Token       string
    CookieName  string
    AllowOrigins []string
}
```

令牌来源（环境变量 `JCP_AUTH_TOKEN`）：

```bash
openssl rand -hex 32      # 生成 64 位十六进制 = 256 位熵
```

### 2.2 三种传递方式

| 方式 | Header/参数 | 适用 |
|------|------------|------|
| Bearer | `Authorization: Bearer <token>` | 普通 fetch 请求（**推荐**） |
| Query | `?token=<token>` | EventSource（无法设置请求头） |
| Cookie | `jcp_token=<token>` | 手动设置 |

### 2.3 比较方式

用 `crypto/subtle.ConstantTimeCompare` 做恒定时间比较，避免时序侧信道：

```go
return subtle.ConstantTimeCompare([]byte(got), []byte(cfg.Token)) == 1
```

### 2.4 公开端点

以下路径**跳过鉴权**：

```go
func isPublicPath(path string) bool {
    switch {
    case path == "/api/health":        return true
    case strings.HasPrefix(path, "/assets/"): return true
    case path == "/" || path == "/index.html": return true
    case path == "/favicon.ico":       return true
    }
    return false
}
```

`/api/health` 只返回版本与时间，不含敏感信息。

> **`/favicon.ico` 为什么免鉴权**：浏览器会自动请求站点图标，这个请求不携带
> 任何自定义请求头。若不放行，控制台会持续报 401，属于噪音而非真实故障。
> 前端同时在 `index.html` 里声明了 `<link rel="icon">`，指向真实 PNG 图标，
> 浏览器便不会再请求 `/favicon.ico`。

### 2.5 前端令牌处理

```typescript
// frontend/src/api/client.ts
export function getToken(): string {
  const fromQuery = new URLSearchParams(window.location.search).get('token');
  if (fromQuery) {
    localStorage.setItem('jcp_token', fromQuery);   // URL 里的令牌存入本地
    return fromQuery;
  }
  return localStorage.getItem('jcp_token') || '';
}
```

**注意**：`localStorage` 可被页面内 XSS 读取。因此：

- 必须部署 HTTPS
- 不要引入不可信的第三方脚本
- 令牌建议定期轮换

### 2.6 ⚠️ Query 参数的日志风险

用 `?token=` 访问时，令牌会出现在：

- Nginx 访问日志
- 浏览器历史记录
- Referer 头（如果页面里有外链）

**建议**：首次用 `?token=` 访问后，前端会存入 `localStorage`；之后用户改用不带参数的 URL。生产环境可考虑让 Nginx 对 `/api/events` 的 `token` 参数做日志脱敏：

```nginx
location /api/events {
    # 避免令牌进入访问日志
    access_log off;
    # ...
}
```

## 3. API Key 保护

这是 Web 化改造中最重要的安全设计。

### 3.1 问题

`AIConfig.APIKey` 明文存储在 `config.json`。桌面模式下这没问题（文件在用户本机），但 Web 模式下 `GET /api/config` 会把它返回给浏览器——任何拿到令牌的人都能拿到大模型密钥。

### 3.2 方案：读取脱敏 + 保存还原

```
写入：客户端 POST 明文 Key → 服务端存明文
读取：服务端返回 ******** → 浏览器看不到明文
保存：客户端回传 ******** → 服务端识别为掩码，还原成原明文
```

实现（`internal/webapi/secrets.go`）：

```go
const maskToken = "********"

// MaskConfig 返回脱敏后的配置副本（不修改原对象）
func MaskConfig(cfg *models.AppConfig) *models.AppConfig {
    clone := *cfg
    clone.AIConfigs = make([]models.AIConfig, len(cfg.AIConfigs))
    copy(clone.AIConfigs, cfg.AIConfigs)
    for i := range clone.AIConfigs {
        clone.AIConfigs[i].APIKey = maskSecret(clone.AIConfigs[i].APIKey)
        clone.AIConfigs[i].CredentialsJSON = maskSecret(clone.AIConfigs[i].CredentialsJSON)
    }
    return &clone
}

// RestoreSecrets 把掩码还原为原明文
func RestoreSecrets(original, incoming *models.AppConfig) {
    for i := range incoming.AIConfigs {
        if incoming.AIConfigs[i].APIKey == maskToken || incoming.AIConfigs[i].APIKey == "" {
            incoming.AIConfigs[i].APIKey = original.AIConfigs[i].APIKey
        }
        // CredentialsJSON 同理
    }
}
```

### 3.3 边界处理

| 情况 | 行为 |
|------|------|
| 掩码值 `********` | 保留服务端原明文 |
| 空字符串 | 保留服务端原明文（避免误清空） |
| 新值 | 覆盖（用户主动修改） |
| 新增 AI 配置 | 直接使用传入值 |

### 3.4 生效链路

```go
// web_main.go
binder.WithSanitizer(
    // 响应脱敏
    func(data any) any {
        if cfg, ok := data.(*models.AppConfig); ok {
            return webapi.MaskConfig(cfg)
        }
        return data
    },
    // 请求还原
    webapi.RequestSanitizer(func() *models.AppConfig {
        return app.GetConfig()
    }),
)
```

### 3.5 剩余风险

- **`config.json` 本身是明文** —— 服务器上的文件权限是最后一道防线
- 服务端进程被攻破 → 密钥仍可被读取
- **Vertex AI 的 `credentialsJSON`** 也做了同样处理

### 3.6 文件权限

```bash
chmod 600 /opt/jcp/data/config.json
chown jcp:jcp /opt/jcp/data/config.json
```

Docker 部署时注意宿主目录权限：

```bash
chmod 700 /opt/jcp-src/data
```

## 4. CORS

```go
func (m *Middleware) CORS(cfg AuthConfig) func(http.Handler) http.Handler {
    // 仅当 Origin 在白名单内才设置响应头
    if origin != "" && m.originAllowed(origin, cfg.AllowOrigins) {
        w.Header().Set("Access-Control-Allow-Origin", origin)
        w.Header().Set("Vary", "Origin")
        w.Header().Set("Access-Control-Allow-Methods", "GET, POST, PUT, DELETE, OPTIONS")
        w.Header().Set("Access-Control-Allow-Headers", "Authorization, Content-Type")
    }
}
```

**默认不允许跨域**（`JCP_CORS_ORIGINS` 为空时）。这防止恶意网站从浏览器发起跨站请求盗用你的令牌。

同源访问（同协议+同域名+同端口）不受 CORS 限制——Nginx 反代到同一域名时无需配置。

## 5. 提示词注入

JCP 的 AI 会读取外部数据（新闻、研报、F10、舆情），这些内容理论上可包含注入指令。

### 5.1 已有的缓解

**工具是只读的**。37 个内置工具全部是查询类，没有任何写操作或外部请求能力。攻击者即使完全控制 LLM 的输出，也只能：

- 读取行情、财务、新闻数据
- 无法执行任意命令
- 无法写入文件
- 无法发起外部请求

### 5.2 工具白名单

每个专家只能看到被授权的工具：

```go
type AgentConfig struct {
    Tools []string `json:"tools"`   // 白名单
}
```

给某个专家只配 `get_stock_realtime`，它就看不到 `get_f10_valuation`。

### 5.3 MCP 的风险

MCP 服务器是**外部引入的代码**（尤其是 `command` 类型——会在服务器上启动进程）。这相当于允许第三方代码执行。

**建议**：

- 优先用 `http` / `sse` 类型的远程 MCP
- 用 `command` 类型时，只信任来源明确的 MCP Server
- 不要配置有写权限的 MCP 工具

## 6. 攻击面清单

### 6.1 暴露面

| 端口 | 服务 | 是否需要公网开放 |
|------|------|----------------|
| 22 | SSH | 是（限制来源 IP） |
| 80 | Nginx | 是（如用 Nginx） |
| 443 | Nginx HTTPS | 是（如用域名） |
| 10001 | jcp-server | 无反代时开放；有反代则只监听 127.0.0.1 |

### 6.2 应用层

| 入口 | 防护 |
|------|------|
| `/api/**` | 令牌鉴权 |
| `/api/health` | 公开，仅返回版本与时间 |
| `/favicon.ico` | 公开（浏览器自动请求，无敏感信息） |
| 静态资源 | 公开 |
| SSE | 令牌鉴权（Query 或 Header） |

### 6.3 数据层

| 文件 | 敏感度 | 建议权限 |
|------|-------|---------|
| `config.json` | 🔴 极高（含明文 API Key） | `600` |
| `strategies.json` | 🟡 中（含专家提示词） | `600` |
| `sessions/` | 🟡 中（含讨论历史，可能含持仓信息） | `700` |
| `memories/` | 🟡 中 | `700` |
| `watchlist.json` | 🟢 低 | `600` |
| `logs/` | 🟡 中 | `600` |

## 7. 加固清单

### 7.1 必做

- [ ] `JCP_AUTH_TOKEN` 设置为 ≥32 字节随机值
- [ ] `config.json` 权限 `600`
- [ ] 服务以非 root 用户运行（systemd 的 `User=jcp`）
- [ ] 云防火墙仅放行 22 与 10001
- [ ] SSH 限制来源 IP
- [ ] 定期轮换令牌（建议每 3 个月）

### 7.2 强烈建议

- [ ] 配置 HTTPS（`?token=` 方式在 HTTP 下会明文传输令牌）
- [ ] 数据备份（含 `config.json`，注意备份本身也含密钥）
- [ ] 开启腾讯云控制台的实例监控告警
- [ ] 定期检查 `journalctl -u jcp-web` 中的异常请求

### 7.3 进阶

- [ ] 前端 CSP 头（限制脚本来源）
- [ ] Nginx 限流（`limit_req` 对 `/api/` 生效）
- [ ] 出网白名单（限制服务器只能访问必要的数据源与大模型 API）
- [ ] 独立的数据目录权限与备份加密

### 7.4 Nginx 限流示例

```nginx
location /api/ {
    limit_req zone=jcp_api burst=10 nodelay;
    proxy_pass http://jcp_backend;
    # ...
}

http {
    limit_req_zone $binary_remote_addr zone=jcp_api:10m rate=10r/s;
}
```

注意：`/api/events` 是长连接，**不要**加限流。

## 8. 自检清单

部署完成后跑一遍：

```bash
# 1. 无令牌访问应 401
curl -o /dev/null -w "%{http_code}\n" http://<IP>:10001/api/config
# 期望：401

# 2. 错误令牌应 401
curl -o /dev/null -w "%{http_code}\n" -H "Authorization: Bearer wrong" http://<IP>:10001/api/config
# 期望：401

# 3. 正确令牌应 200
curl -o /dev/null -w "%{http_code}\n" -H "Authorization: Bearer $TOKEN" http://<IP>:10001/api/config
# 期望：200

# 4. 配置里的 apiKey 应被脱敏
curl -H "Authorization: Bearer $TOKEN" http://<IP>:10001/api/config | grep -o '"apiKey":"[^"]*"'
# 期望："apiKey":"********"

# 5. 业务端口不应绕过鉴权直连
# 在另一台机器上执行，应连接失败
curl --max-time 5 http://<IP>:10001/api/health
# 期望：连接被拒绝或超时（如果走 Nginx 访问 80/443）

# 6. 服务以非 root 运行
ps -o user,cmd -p $(pidof jcp-server)
# 期望：USER 为 jcp 而非 root
```

## 9. 密钥泄露后的处置

若怀疑 API Key 泄露：

1. **立即在模型厂商后台吊销密钥**，重新生成
2. 在 JCP 界面更新 `AIConfig.APIKey`
3. 检查账单是否有异常调用
4. 检查 `journalctl -u jcp-web` 是否有异常请求模式
5. 轮换 `JCP_AUTH_TOKEN`
6. 轮换实例 SSH 密钥对
