### 2.3 时区口径

A股与服务器同为 **UTC+8**（Asia/Shanghai），**无夏令时**，时区不构成问题。
但仍需注意：

- **服务器系统时区**：`2026-10-30 10:46:49 CST` = Asia/Shanghai (UTC+8)
- **新浪 ETF 列表** 的 `ticktime` 字段为 `11:19:40`（北京时间，无日期）
- **新浪 IOPV 接口** 返回完整时间戳：`2026-10-30,11:18:20,4.0769`

> ⚠️ **裁决 D-07**：落库与传输的时间戳一律 **RFC3339 带偏移**

> ETF 的 IOPV 分时序列若存裸时间，跨时区场景会错乱。
> 现在立规范成本几乎为零，后期改要动所有历史数据。

> ⚠️ **不引入 `time/tzdata`**：A股无夏令时，用 `time.FixedZone("CST", 8*60*60)` 即可，
> 避免精简 Linux 镜像缺 `/usr/share/zoneinfo` 的静默失败风险。

## 3.4 🔴 主理人复核发现的 P0（TDX 对 ETF 当前不可用）

> 本节由主理人二次复核补入。原报告 §2.1/§3.1 的「TDX 直接可用」结论
> **前提有误** —— 那是**初始化 `DefaultCodes` 之后**才成立的。
> 详见 [Phase2-口径裁决记录.md §十 D-14](Phase2-口径裁决记录.md)。

### 根因（代码层面逻辑链闭合）

```go
// tdx/client.go:323-332
for i := range codes {
    codes[i] = protocol.AddPrefix(codes[i])
    if !protocol.IsStock(codes[i]) {
        if DefaultCodes == nil {
            return nil, errors.New("DefaultCodes未初始化")   // ← 循环内 return
        }
    }
}
```
- `isSHStock` 只认 `code[:1]=="6"` → `510300` 不是股票
- `isSZStock` 只认 `0`/`30` 开头 → `159915` 不是股票
- **jcp 全库 `grep DefaultCodes` 零命中** → 永远是 nil

### 后果：混合批次整批失败

| 请求 | 结果 |
|---|---|
| `GetQuote("sh600000")` | ✅ 正常 |
| `GetQuote("sh510300")` | ❌ `DefaultCodes未初始化` |
| `GetQuote("sh600000","sh510300")` | ❌ **整批失败**（循环内 return） |

> ⚠️ **这是现存 bug，不只是新增功能受影响** ——
> 用户自选股里只要有一只 ETF，同批所有个股行情都会失败。

### 第二道坎：价格 Decimal 换算缺失（主理人补充发现）

`market_provider_tdx.go:75` 直接 `quote.K.Close.Float64()`，**未做换算**。
TDX 公式为 `p × 10^(2-Decimal)`：

| 标的 | Decimal | 换算 | 不换算的后果 |
|---|---|---|---|
| 个股 `sh600000` | 2 | ×1 | 正确（现网无感） |
| **ETF `sh510300`** | **3** | **÷1000** | **4.105 → 4105** |

### 第三道坎：TDX 搜索目录排除 ETF

`market_provider_tdx.go:359-361`：`if !protocol.IsStock(symbol) { continue }`
→ ETF 根本不在 TDX 搜索目录里。且 TDX 名称是简称
（`GetName("sh510300")="300ETF"`），展示需用新浪/smartbox 全名覆盖。

### 修复要求（3 项，缺一不可）

1. 初始化 `DefaultCodes`（方案 B：自维护 `map[symbol]decimal`，复用
   `tdx_stock_catalog.json` 缓存范式，不引入 sqlite 与每日定时任务）
2. **价格 Decimal 换算**（`p × 10^(2-Decimal)`）
3. **批量请求隔离** —— ETF 与个股分批送 TDX

**外加（主理人裁决 D-14 副二）**：价格合理性断言 ——
ETF 价格须落在 `[0.01, 10000]`，越界判定换算失败并降级到新浪/交易所源。
现有代码**无任何价格断言**，换算出错就是静默错值。

### 其它复核修正

- **深交所 `data.groupId` 完全不可用于 T+0 判定** —— 实测**所有 ETF 都是 8**，
  它只说明「是 ETF」。比原报告「不能区分境内/跨境」的推断更严重。
- **`ReversedBytes3` 对深市 ETF = 昨收单位净值×10000**（4 位精度）：
  sz159915→25341（=2.5341×10000 ✅）、sz159919→42991 ✅；沪市恒 0。
  → 深市 ETF 昨日单位净值可从 TDX 免费拿到，沪市走东财。
- **`ReversedBytes3` 对个股是**无意义值**（66626/132860），不可当净值用。

## 4. 代码改造点评估

### 4.1 Provider 抽象：ETF-only 场景下的最小必要改动

**现状**（`internal/services/market_provider.go`）：
```go
type marketProvider interface {
    FetchStockDataWithOrderBook(codes ...string) ([]StockWithOrderBook, error)
    FetchKLineData(code string, period string, days int) ([]models.KLineData, error)
    FetchMarketIndices() ([]models.MarketIndex, error)
    SearchStocks(keyword string, limit int) ([]StockSearchResult, error)
}
ms.primaryProvider  = newTDXMarketProvider()   // 只支持 SH/SZ/BJ
ms.fallbackProvider = newSinaMarketProvider(ms)
```

#### 主理人裁决 D-01：**ETF 不需要 Provider Map**

主理人核对代码后确认（`market_provider_tdx.go:53-125`）：

```go
quotes, err := cli.GetQuote(codes...)   // ← 不区分个股/ETF
symbol := quote.Exchange.String() + quote.Code
```

TDX 主源的取数路径**完全不区分资产类型** —— 任何 8 位带市场前缀的代码走同一条路；
新浪兜底源（`market_service.go:244-263`）同样按位置解析字段，不区分资产类型。

**因此**：
- `FetchStockDataWithOrderBook` / `FetchKLineData` **不为 ETF 写任何分支逻辑**
- **不需要 Provider Map，不需要按市场前缀分组的批量路由**
- 原方案 A（Provider Map，~150 行新文件 + 4 个方法各改 10 行）**在本期是过度设计**

> 保留原方案分析作为**未来扩展多市场时的参考**（若将来加港股/美股，
> Provider Map 仍是正确演进方向），但本期不做。

#### 本期真正需要的：一个 ETF 元数据的窄接口

新增 `internal/services/etf_metadata_provider.go`：

```go
// ETFMetadataProvider 只负责 ETF 的元数据与净值，
// 与行情管道解耦 —— IOPV 秒级、净值 T+1、规模季度，刷新节奏各不相同。
type ETFMetadataProvider interface {
    // FetchIOPV 取盘中参考净值（新浪 {code}_iopv，27ms）
    FetchIOPV(code string) (iopv float64, ok bool, err error)
    // FetchNAVSeries 取历史单位净值序列（东财 f10/lsjz，分页）
    FetchNAVSeries(code string, limit int) ([]NAVPoint, error)
    // FetchProfile 取产品档案（东财 pingzhongdata：规模/份额/持仓/资产配置）
    FetchProfile(code string) (*ETFProfile, error)
    // ListETFs 取 ETF 全列表（新浪 node=etf_hq_fund，1715 只，缓存 12h）
    ListETFs(keyword string, limit int) ([]ETFListItem, error)
}
```

**为什么不塞进 `marketProvider`**：
①IOPV 来源与行情源不同（新浪 `_iopv` 独立接口）②刷新节奏不同
（秒级 / 实时 / T+1 / 季度）③失败模式不同，混在一起无法区分
「行情整体失败」与「IOPV 取不到」④`/api/stock/realtime` 是 SSE 高频轮询，
塞入持仓/规模会撑爆响应体（裁决 D-02）。

#### 唯一需要改的现有签名

- `SearchStocks(keyword, limit)` → ETF 搜索需返回**类型 + 市场**，
  `StockSearchResult` 需加 `AssetType`/`SecurityType` 字段（见 4.3）。
  影响面：`stock_search.go` + 前端 `types.ts`。
- `FetchMarketIndices()` **保持不变** —— 本期不引入新的指数市场。

### 4.4 ETF 特有能力：塞进现有响应还是新接口？

**建议：不塞进现有行情响应，走新接口。** 理由：

1. 现有 `/api/stock/realtime` 是**高频轮询**接口（前端 SSE 推送用），加 IOPV/净值/持仓会让响应体积暴涨（持仓 10 条 + 净值序列）。
2. IOPV 和净值是**不同更新频率**的数据：IOPV 秒级刷新，净值 T+1 披露，规模季度披露。
3. 持仓/规模是**低频静态数据**，应该缓存。

**建议新增端点**（`internal/webapi/routes.go`，现有 60 个端点 → 70 个）：
